# Drizzle ORM Conventions

`AGENTS.md` §D (Rules 15–18) and §H (Rules 29–37) are the enforced, numbered rules — read those
first. This file is the deeper reference: the patterns those rules assume you know.

## Driver and pool

`postgres` (postgres.js) via `drizzle-orm/postgres-js`. `src/db/client/index.ts` is the app's one
real pool and is **configured, not defaulted** (Rule 38): `max`, `idle_timeout`, `connect_timeout`,
`max_lifetime`, plus `connection.statement_timeout` and
`idle_in_transaction_session_timeout` — the two settings that stop a stuck query or an
abandoned transaction from holding a pooled connection forever.

`{ max: 1 }` there is the anti-pattern (Rule 17,
`.claude/anti-patterns/postgres-max-1-pool.md`) because it serializes every concurrent request.
`src/db/client/migrate.ts` is the one place `{ max: 1 }` is correct.

Behind a transaction-mode pooler (PgBouncer, Supabase pooler) set `DB_PREPARE=false` — server-side
prepared statements do not survive a connection being handed to another transaction.

## Schema location

`src/db/schema/`, one file per domain, re-exported from `schema/index.ts`:

| File | Owns | Note |
|---|---|---|
| `auth.ts` | `user`, `session`, `account`, `verification` | **better-auth owns this shape.** Regenerated by `@better-auth/cli`; do not hand-edit the columns |
| `<domain>.ts` | `<tables>` | One file per domain; list each one here |

Add a new domain as a new file plus one line in `index.ts` — do not grow an existing file past
Rule 26's 200 lines.

## Schema conventions

```ts
// Reusable column bundle — spread into every table instead of retyping it.
// mode:"date" avoids the string<->Date conversion on every read; precision 3
// is millisecond accuracy without the storage of microseconds.
export const timestamps = {
  createdAt: timestamp("created_at", { mode: "date", precision: 3, withTimezone: true })
    .defaultNow()
    .notNull(),
  updatedAt: timestamp("updated_at", { mode: "date", precision: 3, withTimezone: true })
    .defaultNow()
    .notNull()
    .$onUpdateFn(() => new Date()),
};

export const things = pgTable(
  "things",
  {
    // Identity columns over `serial` — serial is legacy in modern Postgres.
    id: integer("id").primaryKey().generatedAlwaysAsIdentity(),
    ownerId: integer("owner_id")
      .references(() => users.id, { onDelete: "cascade" })
      .notNull(),
    status: thingStatusEnum("status").default("draft").notNull(),
    title: varchar("title", { length: 255 }).notNull(),
    ...timestamps,
  },
  (table) => [
    // Rule 32: a REFERENCES column gets NO index automatically. Always add one.
    index("things_owner_idx").on(table.ownerId),
    // Keyset pagination index — matches the ORDER BY in the query below exactly.
    // `.nullsFirst()` is load-bearing: Drizzle's `.desc()` emits `DESC NULLS
    // LAST` on an index, but `orderBy(desc(col))` in a query emits plain
    // `DESC`, which Postgres reads as `NULLS FIRST`. Mismatch the two and the
    // planner cannot take the ordering from the index — it adds a Sort node on
    // top of the index scan and reads every matching row before the LIMIT.
    index("things_created_idx").on(
      table.createdAt.desc().nullsFirst(),
      table.id.desc().nullsFirst(),
    ),
  ],
);
```

Do not hand-write a row type: `typeof things.$inferSelect` / `$inferInsert`. For request and
response Zod schemas derive with `drizzle-zod` (`createInsertSchema` / `createSelectSchema`)
rather than maintaining a parallel shape that can silently drift from the table.

## Index strategy (Rule 32)

| Need | Index |
|---|---|
| Equality or range on one column | `index("t_col_idx").on(table.col)` |
| Filter on A, then sort by B | `index(...).on(table.a, table.b.desc().nullsFirst())` — equality column first, sort column last. **`.nullsFirst()` is required** for the index to satisfy a plain `ORDER BY b DESC`; see the schema example above |
| Query always carries the same constant predicate | partial: `.where(sql\`${table.status} = 'active'\`)` |
| Read one extra column on every hit | covering: `.include(table.total)` — avoids the heap lookup |
| `jsonb` containment or array membership | `.using("gin", table.metadata)` |
| Uniqueness that the app relies on | `uniqueIndex(...)`, not a `UNIQUE` check in the service |

Composite index column order is not cosmetic: an index on `(a, b)` serves `WHERE a = ?` and
`WHERE a = ? AND b = ?`, but not `WHERE b = ?`. Over-indexing costs writes — add the index the
query needs, not one per column.

## Queries

**Column projection (Rule 30).** A bare `db.select().from(t)` ships every `text`/`jsonb` column
on every request:

```ts
// FORBIDDEN on a table with wide columns
const rows = await db.select().from(things);

// ALLOWED
const rows = await db
  .select({ id: things.id, title: things.title, status: things.status })
  .from(things)
  .limit(50);
```

**Keyset pagination (Rule 29).** O(1) at any depth, and — unlike `OFFSET` — cannot skip or
duplicate rows when data changes mid-traversal. Needs the composite index shown above:

```ts
const rows = await db
  .select({ id: things.id, title: things.title, createdAt: things.createdAt })
  .from(things)
  .where(cursor ? lt(things.createdAt, cursor) : undefined)
  .orderBy(desc(things.createdAt), desc(things.id))
  .limit(limit + 1); // one extra row = "has next page", no COUNT needed
```

`.offset()` only for an admin table known to stay small; write the assumed row ceiling in a
comment when you use it.

**Batching instead of N+1 (Rule 31).**

```ts
// FORBIDDEN — one round trip per id
for (const id of ids) rows.push(await db.select().from(things).where(eq(things.id, id)));

// ALLOWED
const rows = await db.select().from(things).where(inArray(things.id, ids));
```

**Relational query builder vs. manual joins.** `db.query.x.findMany({ with: {...} })` emits a
**single** statement using `LEFT JOIN LATERAL` + `json_agg` — it is not an N+1 in disguise, and
`columns` is applied as a partial select at the query level so no extra data leaves Postgres:

```ts
const rows = await db.query.things.findMany({
  columns: { id: true, title: true },
  with: { owner: { columns: { id: true, name: true } } },
  limit: 20,
});
```

Use core `db.select()` with explicit joins when you need aggregation (`extras` does not support
aggregates) or a shape the RQB cannot express.

**Counting.** Prefer `db.$count(things, where)` over selecting rows to count them, and prefer
the `limit + 1` trick above over any count at all on a large table — an exact `COUNT(*)` scans
the whole matching set every time.

**Writes (Rule 36).**

```ts
await db.insert(things).values(rows); // one statement for N rows

await db
  .insert(things)
  .values(row)
  .onConflictDoUpdate({ target: things.slug, set: { title: row.title } }); // not select-then-insert
```

**Prepared statements (Rule 34).** For queries that run on every request:

```ts
const findThingById = db
  .select({ id: things.id, title: things.title })
  .from(things)
  .where(eq(things.id, sql.placeholder("id")))
  .prepare("find_thing_by_id");

const rows = await findThingById.execute({ id });
```

The SQL is concatenated once and Postgres reuses the parsed plan. This buys nothing on a query
that is slow to *execute* rather than slow to *parse*, and nothing on a query that runs once —
do not prepare admin or migration-style queries.

## Transactions (Rule 35)

Transaction boundaries live in the repository — a service needing one is itself a Rule 4
escalation trigger for adding `<module>.repository.ts`:

```ts
await db.transaction(async (tx) => {
  await tx.insert(orders).values(order);
  await tx.update(inventory).set({ count: sql`${inventory.count} - 1` }).where(...);
});
```

Nothing non-DB goes inside: no HTTP call, no Redis round trip, no queue publish. Each of those
holds a connection and its row locks open for the duration of something Postgres cannot see.
Publish side effects *after* the transaction commits.

## Proving a query (Rule 33)

Before merging a query against a table expected to exceed ~100k rows:

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
```

Paste the output in the PR. Look for `Seq Scan` on the hot path (missing or unusable index),
`Rows Removed by Filter` far exceeding the rows returned (the index is not selective enough),
and a planner row estimate off by an order of magnitude from actual (stale statistics, or a
predicate the planner cannot reason about).

`query.toSQL()` prints the SQL and parameters Drizzle will send — use it to build the EXPLAIN,
and to assert in tests that an index-sensitive query still has the shape the index was built
for.

## Migrations

- `bun run db:generate` (drizzle-kit) generates SQL under `src/db/migrations/` from the schema.
  Never hand-edit generated files.
- `bun run db:migrate` runs `src/db/client/migrate.ts` against `DATABASE_URL`. Against
  production it runs as the owner role, from a person's own shell, never through an agent.
- A data backfill a schema change needs is a custom migration: `bun run db:generate --custom
  --name <what>` (the project's own drizzle-kit), then a person writes its replay-safe SQL body
  (AGENTS.md Rule 16).
- `scripts/check/migrations.sh` (CI) re-runs `db:generate` and fails if the directory is dirty —
  i.e. you changed the schema without committing the migration.
- `scripts/check/index-coverage.sh` (CI) fails if a `.references(` column has no index in the
  same schema file (Rule 32).
- agent-be-hono's `migration-guard` hook blocks the agent from writing into
  `src/db/migrations/**` (every folder in `migrationsDirs`).
