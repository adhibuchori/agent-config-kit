# 3D scenes: three.js and React Three Fiber

A WebGL scene is the heaviest thing a page can carry: a large library, binary assets, a GPU context
and a render loop. Each rule below prevents one way that goes wrong: an empty box on first paint, a
phone that heats up while the scene is off-screen, motion a visitor asked not to see, memory that
grows with every visit, a hero that downloads more than the rest of the site. They apply to three.js
used directly and to React Three Fiber (R3F) alike. This file loads when a scene or asset file is
touched; if the 3D code lives elsewhere, add its folder to `paths` above.

## 1. Gate the scene

- The page is complete without WebGL. The scene enhances it: nothing a visitor needs (text, links,
  calls to action) exists only inside the canvas.
- three.js loads only in the browser, and only on pages that show a scene: `next/dynamic` with
  `ssr: false`, called from a client component (`'use client'`), with the still as its `loading`.
  Never import `three`, `@react-three/fiber` or `@react-three/drei` from a server component, a shared
  layout or a module every page imports.
- Mount the canvas when it is about to scroll into view (an `IntersectionObserver` with a margin),
  not on page load. Stop rendering when it leaves the viewport or the tab is hidden
  (`document.visibilityState`).
- Check for WebGL before mounting (`canvas.getContext('webgl2')`, then `'webgl'`), and treat a
  `webglcontextlost` event as a failure that brings the still back.
- Where the browser exposes a data-saving request (`navigator.connection?.saveData`), show the still.
  Feature-detect it: not every browser has it.
- Render on demand. R3F: `frameloop="demand"` and `invalidate()` after a change. three.js: render
  after a change, and `renderer.setAnimationLoop(null)` while nothing moves. A continuous loop is for
  a scene that animates continuously, and it never runs while the scene cannot be seen.
- One canvas per page. Browsers cap live WebGL contexts and drop the oldest with only a console
  warning, so a canvas per card or list item breaks once the list grows: draw several views from one
  shared canvas (scissored viewports, drei's `View`).
- Cap the pixel ratio: R3F `dpr={[1, 2]}`, three.js
  `renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2))`. A 3x screen at full ratio renders
  nine times the pixels of 1x for little visible gain.

## 2. A still fallback, always

- Every scene has a still: an image of its resting frame (`next/image` with `width` and `height`,
  loaded eagerly when it is above the fold), with alt text that says what the scene shows, or
  `alt=""` when it is decoration.
- The still is what renders on the server, while three.js loads, without WebGL, after a lost
  context, under reduced motion and when data saving is on. The scene replaces it only after drawing
  its first frame.
- The still and the canvas fill the same box (the same `aspect-ratio`), so the swap moves nothing:
  no layout shift.
- A `<canvas>` is not a Largest Contentful Paint candidate. A hero that is only a canvas leaves the
  visitor an empty box until the library has downloaded, parsed and drawn; the still, or the text,
  is what paints first.
- When the still or nearby text carries the meaning, the canvas gets `aria-hidden="true"`. When the
  scene is the content, the canvas gets `role="img"` and an `aria-label`. Every pointer interaction
  (orbit, drag, hover) has a keyboard or button equivalent with a visible focus.

## 3. Reduced motion

- Under `prefers-reduced-motion: reduce`: no autoplaying animation, camera moves, auto-rotation,
  parallax or scroll-driven motion. Show the still, or draw one frame and move only in direct
  response to the visitor's input.
- Read it with `matchMedia('(prefers-reduced-motion: reduce)')` and listen for its `change` event:
  the setting can change while the page is open.
- Reduce means remove, not slow down.
- Animation that starts on its own and runs longer than five seconds next to other content has a
  visible pause control (WCAG 2.2.2, Pause, Stop, Hide).

## 4. Dispose what you create

- three.js frees no GPU memory on its own. Removing an object from the scene leaves its geometry,
  material and textures on the GPU.
- On unmount, call `dispose()` on every geometry, material, texture and render target the component
  created. `material.dispose()` does not dispose the material's textures: dispose them as well.
  Dispose post-processing passes and composers that own render targets, and the renderer when its
  canvas goes away for good.
- R3F disposes what it created from JSX when that unmounts. Do not rely on it for anything else:
  objects made with `new THREE.*` (in a `useMemo`, for example), loader results kept in a cache, and
  objects passed through `<primitive object={…} />` are yours to dispose; check what your R3F version
  disposes. A cached asset that another component still shows gets `dispose={null}`, so one unmount
  does not free it for everyone.
- On unmount, also remove what the scene added outside itself: resize and pointer listeners,
  observers, the `webglcontextlost` listener, timers and animation loops.
- Verify, do not assume: `renderer.info.memory.geometries` and `.textures` (R3F:
  `useThree((state) => state.gl).info`) return to their earlier values after the scene unmounts and
  mounts again. A count that grows on every navigation is a leak.

## 5. Asset budgets

- `node scripts/check/3d-budget.mjs` checks every model, texture and environment map under the roots
  in `scripts/check/3d-budget.json` against its budget, and says how many files it read. It runs with
  the other gates once `scripts/check/gates.list` has its line.
- The defaults are starting points: a model 1.5 MB, counting every buffer and image it points at,
  and 100,000 triangles as rendered; a texture 512 KB and 2048 px on its longer side; an environment
  map 2 MB. Measure on a mid-range phone, then tighten or loosen them in the config.
- A file that needs more gets an `exceptions` entry with its reason. Never raise a budget for every
  file to make room for one.
- Meet a budget at the source: compress geometry (Draco or Meshopt; the glTF Transform tools do
  both), ship textures as KTX2 (Basis Universal), WebP or AVIF at the size the camera actually shows,
  bake lighting instead of computing shadows live, and prefer a small prefiltered environment map to
  a large HDR.
- Serve the decoders that compressed assets need (the Draco decoder, the KTX2 transcoder) from your
  own origin, not a third-party CDN, so the page's CSP, the visitor's privacy and the scene's
  availability depend on nobody else.
- Load what the first frame needs; fetch the rest after it has drawn.

## It's working if

- `next build` shows the scene's page carrying three.js in its own chunk, not in the first-load
  JavaScript every page shares.
- With WebGL turned off in the browser, or reduced motion on, the page shows the still, and nothing
  moves or shifts.
- A performance recording shows no animation frames while the scene is off-screen or the tab is
  hidden.
- `renderer.info.memory` returns to its baseline after leaving the page and coming back.
- `node scripts/check/3d-budget.mjs` passes and names how many models, textures and environment maps
  it read.

## Supply-chain and upgrade traps

- A skill or a README that runs an **unscoped** package through a package runner (for example a
  model optimiser's CLI under a bare name) runs whatever currently owns that name, which can be
  unpublished and re-claimed. Run the maintainer's scoped package at a pinned version instead, and
  refuse the bare name.
- Before a React upgrade, check the React peer range of `@react-three/fiber` (and drei): a renderer
  that does not support the new major fails at runtime, not at install.
